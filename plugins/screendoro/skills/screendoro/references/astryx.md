# Astryx 사용 (astryx)

컴포넌트 라이브러리로 [Astryx](https://github.com/meta/astryx)(`@astryxdesign/*`, Meta의 오픈소스 디자인 시스템, 베타)를 쓰는 프로젝트에만 적용하는 문서다. **선택 사항**이다. 마커의 `componentLib`이 `"astryx"`일 때만 읽는다.

역할: Astryx는 **부품과 테마 엔진**만 맡는다. 디자인 방향(1단계 시안, `DESIGN.md`), 구현 지침(`frontend-design`), 검증(4단계)은 Astryx를 써도 그대로 수행한다.

우선순위: 사용자 지시 > `house-rules.md` > 프로젝트 `DESIGN.md` > 이 문서를 포함한 `references/` 문서 > `frontend-design` 기본값 > **Astryx 기본값**(기본 테마의 모양, Astryx가 프로젝트에 써 넣은 에이전트 안내).

Astryx는 베타라 명령과 토큰 이름이 바뀔 수 있다. 이 문서에 적힌 이름보다 설치된 CLI가 출력하는 내용을 믿는다.

---

## 1. 판별 (0단계)

위에서부터 처음 맞는 줄을 따른다.

| 상태 | 처리 |
|---|---|
| 마커에 `componentLib`이 있다 | 그 값을 따른다. 묻지 않는다 |
| `package.json`에 `@astryxdesign/core`가 있다 | Astryx 프로젝트다. 마커에 `"componentLib": "astryx"`를 적는다. 묻지 않는다 |
| 마커는 있는데 `componentLib`이 없다 | 쓰지 않는 것으로 본다. 묻지 않는다 |
| 1단계를 건너뛰는 프로젝트 (이미 프론트엔드 환경이 있다) | `"none"`. 묻지 않는다 |
| React 18 이하, Vue·Svelte 등 다른 프레임워크, 빌드 없는 정적 HTML | `"none"`. 묻지 않는다 |
| 1단계를 수행하고(최초 구성), React 19 이상이거나 프레임워크를 아직 정하지 않았다 | AskUserQuestion으로 **한 번** 묻는다 |

질문할 때:

- 선택지는 "쓰지 않음"(기본값)과 "Astryx 사용" 두 개다.
- Astryx는 표, 폼, 설정, 상세 페이지 같은 앱 화면에 강하고 랜딩에서는 이점이 적다는 것, 베타라는 것을 설명에 한 줄로 적는다.
- 답이 없거나 "알아서"라고 하면 **쓰지 않음**으로 진행하고 그렇게 했다고 한 줄로 알린다.
- 사용자가 처음부터 "Astryx로 만들어 줘"라고 했으면 묻지 않고 사용한다.

이미 환경이 있는 프로젝트에 나중에 Astryx를 넣는 것은 사용자가 요청할 때만 한다. 기존 화면을 Astryx로 바꾸는 범위를 먼저 사용자와 정하고, 2~3절을 수행한 뒤 마커를 고친다.

## 2. 설치와 연결 (1단계, 시안을 고른 뒤)

1-1 시안은 Astryx 없이 지금처럼 정적 HTML로 그린다. 시안은 방향을 고르는 용도이고, Astryx 컴포넌트로 옮기면 세부 모양이 조금 달라질 수 있다고 시안을 보여줄 때 한 줄로 알린다.

사용자가 시안을 고른 뒤에 아래 순서로 붙인다.

1. **설치**: `@astryxdesign/core`, 테마 패키지 하나(`@astryxdesign/theme-<이름>`), `@stylexjs/stylex`를 의존성으로, `@astryxdesign/cli`를 개발 의존성으로 넣는다. 프로젝트가 쓰는 패키지 매니저를 따른다.
2. **`init`**: `npx @astryxdesign/cli init`을 실행한다. 이 명령은 프로젝트의 `CLAUDE.md`/`AGENTS.md`에 Astryx 안내를 써 넣으므로, 실행 전에 그 사실을 한 줄로 알린다. 써 넣은 안내와 screendoro가 다르면 5절을 따른다.
3. **CSS import 순서**: `reset.css` → `astryx.css` → 테마의 `theme.css`. 순서가 우선순위를 정하므로 바꾸지 않는다.
4. **Tailwind를 같이 쓰면**: `@layer` 선언 줄이 Tailwind import보다 **위에** 있어야 한다. 아래에 두면 오류 없이 우선순위만 뒤집힌다. 정확한 내용은 `docs styling-libraries/tailwind`로 확인한다.
5. **테마 프로바이더**: 앱 루트를 `Theme`로 감싼다.

프레임워크별 정확한 코드(Next.js, Vite 등)는 설치한 버전의 문서를 조회해서 쓴다. 기억으로 쓰지 않는다.

## 3. `DESIGN.md`를 테마로 옮기기 (1단계)

- 기본 테마 7종(neutral, butter, chocolate, matcha, stone, gothic, y2k) 중 고른 시안과 가장 가까운 것을 바탕으로 삼고, 마커 `astryxTheme`에 적는다.
- `DESIGN.md`의 색, 반경, 간격, 폰트 값을 **테마의 토큰 오버라이드**로 옮긴다. Astryx 테마는 CSS 커스텀 프로퍼티 묶음이다.
- 토큰 이름은 `docs tokens`, 테마를 정의하는 방법은 `docs theme`으로 조회한 뒤 쓴다.
- 값은 테마 한 곳에서 바꾼다. 같은 값을 컴포넌트마다 `className`으로 덮지 않는다.
- `DESIGN.md`에 "컴포넌트는 Astryx를 쓴다"는 것과 바탕 테마, 바꾼 토큰을 **이유와 함께** 적는다.

고정 규칙은 이렇게 반영한다.

| 고정 규칙 | Astryx에서 |
|---|---|
| 경기천년체 | 폰트 토큰을 경기천년제목(제목·버튼)과 경기천년바탕(본문)으로 지정한다 |
| 버튼 반경 8px 이상 | `component Button`으로 버튼이 쓰는 반경 토큰을 확인하고 그 토큰을 8px 이상으로 둔다 |
| 이중 테두리 금지 | 토큰만으로는 막지 못한다. 6절에서 검사하고 고친다 |
| 불필요한 밑줄·요소 금지 | 컴포넌트의 장식 옵션을 켜지 않는다. 6절에서 검사한다 |

폰트에서 주의할 것:

- Astryx 테마는 폰트를 **이름만** 지정하고 파일은 로드하지 않는다. 경기천년체 파일은 `house-rules.md` 1절대로 따로 구한다.
- `body`에 `font-family`를 직접 선언한다. 선언하지 않으면 `font: inherit`인 컴포넌트(버튼 등)의 글자가 브라우저 기본 서체로 나온다.
- 기본 테마 문서가 안내하는 웹폰트 링크(예: Figtree)는 넣지 않는다. 경기천년체로 바꾸므로 필요 없는 요청이다.

## 4. 화면 작성 (3단계)

`frontend-design`을 불러온 뒤, 화면 코드를 쓰기 전에 조회한다. 모든 명령은 `npx @astryxdesign/cli` 뒤에 붙이거나 프로젝트의 패키지 매니저 실행기(`pnpm exec astryx` 등)로 부른다.

| 상황 | 명령 |
|---|---|
| 페이지 전체를 만든다 | `build "<페이지 목적>"` → `template <이름>` |
| 부품이 필요하다 | `search <키워드>` → `component <이름>` |
| 토큰, 테마, 레이아웃 규칙을 확인한다 | `docs tokens`, `docs theme`, `docs layout` |
| 명령이나 옵션이 기억과 다르다 | `<명령> --help` |

- 출력이 길면 `--dense`를 붙인다. 구조화된 값이 필요하면 `--json`을 쓴다.
- 컴포넌트의 props, variant는 `component <이름>`으로 읽은 뒤 쓴다. 한 세션에서 이미 읽은 컴포넌트는 다시 읽지 않는다.
- Astryx에 있는 부품은 직접 만들지 않는다. 없는 부품은 직접 만들되 색, 반경, 간격은 Astryx 토큰을 쓴다.
- 직접 만드는 부분에서도 색과 치수를 하드코딩하지 않고 토큰을 쓴다.
- **앱·대시보드 작업**: 템플릿에서 시작해도 된다. 템플릿의 틀과 간격은 유지하고 내용을 바꾼다.
- **랜딩 작업**: 템플릿에서 시작하지 않는다. 2단계 결과물의 섹션 순서와 고른 시안의 구조를 따르고, Astryx는 버튼, 입력창, 아코디언 같은 부품으로만 쓴다.

## 5. Astryx가 써 넣은 안내와 다를 때

`init`이나 Astryx 플러그인이 넣는 에이전트 안내에는 screendoro와 다른 규칙이 있다. 아래대로 처리한다.

| Astryx 안내 | screendoro에서 |
|---|---|
| 모든 페이지를 템플릿에서 시작한다 | 앱·대시보드에만 적용한다. 랜딩에는 적용하지 않는다 |
| 날 `<div>`·`<span>`, 하드코딩한 색·px를 컴포넌트와 토큰으로 바꾼다 | 따른다. 단, 고정 규칙과 `DESIGN.md`가 우선이다 |
| UI 작업이면 항상 Astryx를 쓴다 | 마커가 `"astryx"`인 프로젝트에서만 쓴다 |
| 전달 전에 빌드한다 | 4단계 렌더링 검증으로 대신한다 |

- Astryx 플러그인(`astryx@astryx`)과 전역 설치(`npm i -g @astryxdesign/cli`)는 사용자에게 묻지 않고 하지 않는다. 둘 다 Astryx를 쓰지 않는 프로젝트에서도 Astryx 안내가 발동하게 만든다.
- screendoro의 단계 순서(0 → 1 → 2 → 3 → 4)는 Astryx 안내 때문에 바뀌지 않는다.

## 6. 검증 (4단계)

- `house-check.js`와 `render-check.md`는 화면에 그려진 결과를 보므로 Astryx 컴포넌트에도 그대로 적용한다. Astryx 컴포넌트라는 이유로 고정 규칙 위반을 봐주지 않는다.
- 위반을 고칠 때는 아래 순서로 시도한다.
  1. **테마 토큰**을 바꾼다 (같은 컴포넌트 전체가 한 번에 고쳐진다).
  2. 해당 위치에 **`className`으로 덮는다**.
  3. **`swizzle <컴포넌트>`**로 소스를 프로젝트로 꺼내 고친다. 꺼낸 컴포넌트는 이후 업그레이드를 직접 따라가야 하므로, 실행 전에 사용자에게 묻는다.
- 키보드 포커스 링은 `house-rules.md` 3절의 예외다. Astryx의 포커스 표시를 지우지 않는다.
- `doctor`를 한 번 실행해 설치 상태에 문제가 없는지 본다. 오류는 필수 항목으로, 경고는 권장 항목으로 정리한다.
- antislop 점검에서, `DESIGN.md`에 이유와 함께 적힌 Astryx 컴포넌트의 기본 모양은 목적 있는 선택으로 본다. 대비·접근성 기준과 고정 규칙은 그대로 적용한다.
- 완료 보고의 "단계" 줄에 Astryx 사용을 적고, `swizzle`한 컴포넌트가 있으면 이름을 적는다.

## 7. 금지 사항

- 사용자가 고르지 않았는데 Astryx를 설치하거나, 마커가 `"astryx"`가 아닌 프로젝트에서 이 문서를 적용하지 않는다.
- CLI를 설치하기 전에 `npx astryx`를 실행하지 않는다. 범위 없는 `astryx`는 무관한 npm 패키지다. 항상 `npx @astryxdesign/cli`를 쓴다.
- 컴포넌트 props, 토큰 이름, 명령 옵션을 기억으로 쓰지 않는다. 조회해서 쓴다.
- Astryx를 쓰려고 React 버전을 올리지 않는다. React 19 미만이면 사용자에게 먼저 묻는다.
- 안정 버전이 없는 패키지(`@canary` 태그로만 배포되는 차트 패키지 등)를 사용자에게 묻지 않고 넣지 않는다.
- 사용자에게 묻지 않고 `swizzle`하지 않는다.
- Astryx의 기본 모양을 이유로 고정 규칙이나 `DESIGN.md`를 어기지 않는다.

## 체크리스트

- [ ] 마커에 `componentLib`(과 `astryxTheme`)이 기록됨
- [ ] CSS import 순서가 `reset.css` → `astryx.css` → `theme.css`
- [ ] `DESIGN.md` 값이 테마 토큰으로 옮겨졌고, 컴포넌트별 덮어쓰기로 흩어져 있지 않음
- [ ] 폰트 토큰과 `body`의 `font-family`가 경기천년체
- [ ] 버튼 반경 8px 이상 (렌더링에서 확인)
- [ ] Astryx 컴포넌트에서 이중 테두리, 장식 밑줄이 나오지 않음
- [ ] 직접 만든 부분에 하드코딩한 색·px가 없음
- [ ] `swizzle`한 컴포넌트가 있으면 완료 보고에 적음
