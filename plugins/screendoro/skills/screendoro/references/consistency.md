# 뽑기 줄이기 (consistency)

같은 요청에도 화면이 매번 다르게 나오고, 좋은 결과가 운에 달리는 문제를 줄이는 절차다. 원칙은 **탐색은 뽑기로, 생산은 조립으로**다.

- **탐색**(2단계 시안): 결과가 다양하게 나오는 것이 장점이다. 여러 개를 만들어 사용자가 고른다.
- **생산**(3단계 화면): 고른 결정을 코드와 규칙으로 굳혀 두고, 화면은 그것을 조립해서 만든다. 매번 새로 그리지 않는다.

`SKILL.md`가 각 절을 읽는 시점을 정한다.

| 절 | 내용 | 읽는 때 |
|---|---|---|
| 1 | 구조 와이어프레임 | 2-1 시안 전 |
| 2 | 레이아웃 문법 | 시안을 고른 뒤 `DESIGN.md`를 쓸 때 |
| 3 | 코드 키트 | 시안을 고른 뒤, 그리고 3단계 조립 때 |
| 4 | 거절 피드백 | 사용자가 시안이나 화면을 거절하거나 다시 그려 달라고 할 때 |
| 5 | 승인 화면 보관과 비교 | 시안을 고른 뒤, 3-4 자기 비평, 4단계 끝 |
| 6 | `design-check.js` 읽는 법 | 3-4 자기 비평, 4단계 렌더링 검증, 키트를 만든 뒤 |
| 7 | 키트가 없는 프로젝트 | 마커는 있는데 키트가 없을 때 |

---

## 1. 구조 와이어프레임 (2-1 시안 전, 프로젝트당 1회)

스타일 시안을 그리기 전에 페이지 **전체**의 구조를 먼저 정한다. 구조와 스타일을 한 번에 뽑으면 하나가 어긋날 때 전체를 다시 뽑게 된다.

- 파일: `.claude/screendoro-mocks/wireframe.html`
- 범위: 대표 화면 전체. 랜딩이면 모든 섹션, 앱이면 메인 화면 전체.
- 모양: 회색 상자와 실제 문구(0-1단계 확정 구조, 1단계 결과물에서 가져온다). 색, 폰트, 장식은 넣지 않는다. 와이어프레임은 화면이 아니라 구조 도면이라 고정 규칙 점검 대상이 아니다.
- 섹션마다 보여 줄 것: 담을 내용, 정보량(항목 수, 글 길이), 화면에서 차지하는 비중(대략의 높이), 첫 화면에 들어가는 범위.
- 사실 주장 자료가 없는 곳은 `landing-strategy.md` 9-2의 교체 자리로 표시한다.

**와이어프레임이 정하는 것**: 섹션 구성과 순서, 섹션별 내용과 정보량, 첫 화면 범위.
**정하지 않는 것**: 배치(그리드, 비율, 정렬), 색, 타이포, 분위기. 이것은 시안끼리 달라야 하는 축이다.

보여 주고 한 번 묻는다: "이대로 / 고칠 곳 있음(자유 서술)". 0-1단계 확정 구조가 있으면 그것을 그린 것이므로 보통 바로 넘어간다. 새로 정해지는 것은 정보량과 첫 화면 범위뿐이다. 답이 없거나 "알아서"면 그대로 진행하고 한 줄로 알린다.

이후 시안은 모두 이 와이어프레임의 구성을 지킨다. 시안의 범위는 **첫 화면 + 대표 섹션 1~2개**다. 대표 섹션은 방향 차이가 가장 잘 드러나는 섹션(근거, 사용 방법, 앱이면 목록이나 상세 영역)을 고르고, 모든 시안이 같은 섹션을 그린다. 첫 화면만 고르면 그 아래는 아무도 고르지 않은 생성물이 된다.

## 2. 레이아웃 문법 (`DESIGN.md` 9절)

토큰(색, 글자, 간격, 반경)만으로는 배치가 매번 새로 생성된다. 고른 시안에서 **배치 규칙**도 뽑아 `DESIGN.md`에 적는다. 값마다 승인 표시(`design-setup.md` 5-3)를 단다. 시안에 보였던 규칙은 `[승인: 시안 X]`, AI가 넓혀 정한 규칙은 `[AI]`다.

~~~markdown
## 9. 레이아웃 문법

### 그리드
- 12열, 최대 폭 1120px, 바깥 여백 모바일 20px · 데스크톱 48px [승인: 시안 B]
- 정렬: 본문은 왼쪽 정렬. 가운데 정렬은 마지막 CTA에만 [승인: 시안 B]

### 섹션 리듬
- 섹션 사이 여백 두 단계: 큰 전환 --space-16, 같은 이야기 안의 전환 --space-8 [승인: 시안 B]
- 면 색은 큰 전환에서만 바꾼다 [AI]
- 같은 유형의 섹션을 연이어 두지 않는다

### 섹션 유형
| 이름 | 언제 | 키트 |
|---|---|---|
| 노선 단계 | 순서가 있는 내용 (사용 방법, 진행 과정) | `src/design/sections/RouteSteps` [승인: 시안 B] |
| 비대칭 진술 | 핵심 주장 하나를 크게 | `src/design/sections/SplitStatement` [AI] |

노선 단계:
```
[제목 ··········· ]
●───────●───────●
단계1    단계2    단계3   (각 단계 아래 설명 2줄)
```

### 시그니처
- 무엇: 역 표시처럼 생긴 원형 마커와 연결선 [승인: 시안 B]
- 어디: 단계, 진행 상태, 첫 화면의 흐름 그림
- 횟수: 한 화면에 한 번만 크게. 나머지는 작은 표시로

### 밀도
- 설득형 화면: 섹션당 항목 3~5개, 본문 2~3줄
~~~

- 섹션 유형 이름은 이 방향에서의 역할로 짓는다 (`RouteSteps`, `SplitStatement`). `FeatureGrid`, `Testimonials` 같은 일반 이름은 일반 생김새를 부른다.
- 섹션 유형은 3~5개로 시작한다. 고른 시안에 보인 섹션, 와이어프레임에서 반복되는 섹션 종류를 기준으로 정한다.
- 시안에서 보이지 않은 유형을 미리 많이 만들지 않는다. 필요할 때 3단계에서 더한다.

## 3. 코드 키트

`DESIGN.md`가 글로 된 결정이라면 키트는 그 결정을 **코드로 굳힌 것**이다. 3단계는 키트를 조립해서 화면을 만든다.

### 3-1. 만들기 (2단계, 시안을 고른 뒤)

`design-setup.md` 6절의 토큰과 기본 구조를 만든 뒤 이어서 만든다.

- **위치**: 프로젝트가 쓰는 관례를 따른다 (기존 디자인 시스템 폴더, `src/components/ui/` 등). 관례가 없으면 `src/design/`. 빌드 없는 정적 HTML이면 `design/kit.css`와 `design/sections/`. 마커 `kitPath`에 적는다.
- **기본 부품**: 주 버튼, 보조 버튼, 입력창, 링크, 내비게이션, 이 방향의 면(카드나 패널을 쓰는 방향이면), 시그니처 요소. Astryx 프로젝트면 Astryx에 있는 부품은 만들지 않고 테마로 맞춘다 (`astryx.md` 3절).
- **섹션 틀**: 2절의 섹션 유형마다 하나. 내용은 props나 슬롯으로 받고, 배치·여백·면 색은 틀 안에 고정한다.
- 색과 치수는 토큰만 쓴다. 키트 안에서도 값을 직접 쓰지 않는다.
- **카탈로그**: 모든 부품과 섹션 틀을 한 페이지에 모은 `.claude/screendoro-mocks/kit.html`(또는 프로젝트의 개발용 경로)을 만든다. 실제 문구를 넣는다. 만든 뒤 `house-check.js`와 `design-check.js`를 돌려 키트부터 규칙을 지키는지 본다.
- `DESIGN.md` 10절 "키트"에 부품과 섹션 틀의 이름, 경로, 승인 표시를 적는다. 고른 시안에 보였던 것은 `[승인: 시안 X]`, 나머지는 `[AI]`다.

### 3-2. 조립하기 (3단계)

- 3-1 계획에서 섹션마다 레이아웃 문법의 **섹션 유형을 고른다.** 계획 줄의 형식: `섹션 이름 → 유형 → 담을 내용`.
- 화면은 키트 부품과 섹션 틀로 만든다. 같은 부품을 화면마다 다시 스타일링하지 않는다. 변형이 필요하면 키트 부품에 변형(prop)을 더한다.
- **맞는 유형이 없을 때만** 새 섹션 틀을 만든다. 계획에 이유를 한 줄 적고, 키트에 `[AI]`로 더하고, 레이아웃 문법 표에도 더한다. 완료 보고에 "승인 대기 키트"로 적는다.
- 키트 부품 자체를 고치면 모든 화면이 바뀐다. 고치기 전에 사용자에게 알린다.
- 3-2 뻔함 점검은 키트 조립에도 그대로 한다. 키트로 만들었다고 뻔함이 면제되지는 않는다.

## 4. 거절 피드백 ("다시 그리기"를 뽑기에서 좁히기로)

사용자가 시안이나 화면을 거절하거나 다시 그려 달라고 하면, 다시 만들기 전에 **어느 축이 문제인지** 한 번 묻는다.

- AskUserQuestion, 여러 개 선택 가능: 배치 / 색 / 타이포(크기·굵기 대비) / 밀도·여백 / 분위기. "Other"에 구체적으로 무엇이 싫은지 적을 수 있다고 질문에 쓴다.
- 사용자가 이미 이유를 말했으면 묻지 않고 그 말을 쓴다.
- **고른 축만 바꾸고 나머지는 유지해서** 다시 만든다. 사용자가 방향 전체가 아니라고 하면 2-1의 기존 규칙(보여준 방향은 빼고 새로)을 따른다.
- `.claude/screendoro-feedback.md`에 기록한다.

```markdown
## YYYY-MM-DD 시안 A 거절
- 축: 밀도·여백, 분위기
- 사용자 말 (그대로): "너무 휑하고 차가워 보여"
- 바꾼 것: 섹션 여백 한 단계 줄임, 바탕을 따뜻한 회색으로. 배치·타이포는 유지
```

- `DESIGN.md`가 생긴 뒤에는, 다시 나올 수 있는 거절 이유를 8절 "하지 않을 것"에 `[승인: 사용자 지시]`로 옮긴다.
- 사용자가 "다른 프로젝트에서도 이건 싫다"고 하면, `~/.claude/screendoro-taste.md`에 적어도 되는지 묻고 허락을 받은 뒤에만 적는다. 이 파일은 0단계에서 읽는다. 우선순위는 고정 규칙(`house-rules.md`) 바로 다음이다. 지금 대화의 사용자 지시가 더 우선한다.

## 5. 승인 화면 보관과 비교

세션이 바뀌면 남는 것이 `DESIGN.md` 토큰뿐이라 화면이 조금씩 다른 제품처럼 흘러간다. 사용자가 받아들인 화면을 실제 모습으로 남겨 기준으로 쓴다.

### 5-1. 보관

- 폴더: `.claude/screendoro-approved/`, 목록 파일 `index.md`

```markdown
| 화면 | 날짜 | 상태 | 캡처 | 소스 |
|---|---|---|---|---|
| 시안 B (첫 화면 + 단계 섹션) | 2026-11-25 | 승인 | sian-b-1280.png, sian-b-375.png | .claude/screendoro-mocks/option-b.html |
| 가격 페이지 | 2026-11-26 | 승인 대기 | pricing-1280.png, pricing-375.png | src/pages/pricing.tsx |
```

- **첫 항목**: 사용자가 고른 시안. 고른 직후 데스크톱(1280)과 모바일(375) 캡처를 저장하고 상태는 "승인"이다.
- **화면**: 4단계를 마치면 같은 두 폭의 캡처를 저장하고 "승인 대기"로 적는다. 사용자가 받아들였다고 말하면 "승인"으로 바꾼다. 고쳐 달라고 하면 고친 뒤 캡처를 바꾼다.
- 캡처 저장은 브라우저 패널의 저장 기능이나 `render-pw.cjs --approved`(1280·375 캡처를 이 폴더로 복사)로 한다. 둘 다 없으면 캡처 칸에 "저장 못 함"이라 쓰고 소스 경로와 `design-check.js` 요약만 남긴다.
- 승인 항목은 최근 10개와 시안만 남기고 오래된 캡처는 지운다.
- 처음 만들 때 이 폴더와 `.claude/screendoro-mocks/`를 git에 올릴지는 사용자가 정할 일이라고 한 줄로 알린다. 묻지 않고 `.gitignore`를 고치지 않는다.

### 5-2. 비교

3-4 자기 비평과 4단계 끝에서, 새 화면 캡처를 "승인" 상태 캡처 1~2장(시안과 가장 가까운 화면)과 나란히 본다.

- 글자 위계: 제목·본문·보조 글자의 크기와 굵기 관계가 같은가
- 시그니처: 같은 규격으로, 같은 횟수로 쓰였는가
- 섹션: 레이아웃 문법의 유형과 리듬을 따랐는가
- 면과 색: 면 색을 바꾸는 규칙, 강조색을 쓰는 곳이 같은가
- 밀도: 정보량과 여백이 비슷한가

이유 없이 다른 곳은 고친다. 이 화면만의 이유가 있으면 계획이나 완료 보고에 적는다. 승인 화면이 아직 없으면 시안 캡처와 비교한다.

## 6. `design-check.js` 읽는 법

`references/design-check.js`는 만든 화면이 `DESIGN.md`의 토큰과 레이아웃 문법을 지키는지 잰다. 읽기만 한다. 토큰은 `:root`의 CSS 변수에서 읽으므로 `design-setup.md` 6절의 이름 규칙을 지켜야 한다.

- **실행 시점**: 3-4 자기 비평(데스크톱 폭), 4단계 렌더링 검증(폭마다, `house-check.js`와 같이), 키트 카탈로그를 만든 뒤.
- **실행 방법**: `house-check.js`와 같다. 파일 내용을 그대로 `javascript_tool`에 넣는다. Playwright 폴백(`render-pw.cjs`)은 폭마다 자동으로 실행해 결과의 `designCheck`에 넣는다.

| 결과 | 뜻 | 등급 |
|---|---|---|
| `offScaleFontSize`, `offPaletteColor`, `offScaleSpacing`, `offScaleRadius` | 토큰에 없는 값 | **필수** (`DESIGN.md` 위반). 토큰 값으로 바꾼다. 꼭 필요한 새 값이면 하드코딩하지 말고 `DESIGN.md`에 토큰으로 더한 뒤 `[AI]`로 적고 보고한다 |
| `repeatedNeighbourSections` | 이어진 두 섹션의 구조가 같음 | 레이아웃 문법의 "같은 유형 연속 금지"를 어겼으면 **필수**, 아니면 권장 |
| `uniformSectionPadding` | 섹션 4개 이상의 위아래 여백이 모두 같음 | 레이아웃 문법에 리듬 규칙이 있으면 **필수**, 아니면 권장 |
| `centeredTitleGridSections` | 가운데 제목 + 3칸 이상 그리드 섹션 | 3개 이상이면 권장 (`slop-tells.md` 2절) |
| `identicalCardGroups` | 크기와 내부 구조가 모두 같은 카드 묶음 | 권장. 그 카드가 레이아웃 문법의 섹션 유형이면 통과 |
| `accentUsage` | 강조색을 쓴 요소 수와 종류(글자, 배경, 테두리) | 참고. 세 종류 모두에 많이 쓰였으면 "강조색 하나를 전부에 칠하기"인지 본다 |
| `sections`, `distinctSectionShapes` | 섹션 수와 서로 다른 구조 수 | 참고. 서로 다른 구조가 섹션 수의 절반 미만이면 리듬을 다시 본다 |
| `note` | 토큰을 못 찾음 | 값 검사가 빠진 것이다. 토큰 선언을 고치거나 보고에 "design-check 값 검사 못 함"이라 적는다 |

- 외부 임베드, 사용자가 올린 콘텐츠처럼 토큰을 적용할 수 없는 영역에는 `data-screendoro-ignore` 속성을 달아 검사에서 뺀다.
- 브라우저 기본 모양이 남은 입력창, 선택 상자 등에서 나온 값도 위반이다. 토큰으로 스타일을 입힌다.
- 섞어 만든 색(`color-mix`, 투명도를 섞은 보조 글자색 등)도 토큰으로 선언한다. 선언하지 않으면 팔레트 밖 색으로 잡힌다.
- 스크립트는 측정일 뿐이다. 최종 판정은 캡처를 보고 한다.

## 7. 키트가 없는 프로젝트

마커는 있는데 키트(`kitPath`)나 레이아웃 문법이 없는 프로젝트(1.7.0 이전에 구성했거나, 이미 프론트엔드가 있던 프로젝트)는 이렇게 한다.

- 3-1 계획 전에 이미 있는 컴포넌트와 화면을 훑어 **기존 부품과 섹션 모양 목록**을 만들고, 그것을 키트로 보고 조립한다. 기존 화면과 다른 새 스타일을 만들지 않는다.
- 이미 승인된 화면이 없으면 기존 주요 화면 1~2개를 띄워 캡처를 5절 비교 기준으로 쓴다 (저장은 하지 않아도 된다).
- 키트와 레이아웃 문법을 정식으로 만드는 것은 사용자가 요청할 때만 한다. 리디자인이 아니라 기존 화면에서 뽑아 정리하는 작업이며, 끝나면 마커에 `kitPath`를 적는다.
- `design-check.js`가 토큰을 못 찾으면 값 검사는 건너뛰고, 구조 반복 결과만 쓴다.
