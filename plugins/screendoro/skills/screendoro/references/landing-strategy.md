# 랜딩 전략 (landing-strategy)

screendoro가 **랜딩·마케팅 페이지 작업일 때만** 읽는 참조 문서다. 대시보드, 앱 화면, 일반 컴포넌트에는 적용하지 않는다.
출처: elayadesign/ai-design-skills `landing-page-design` (MIT). Part A 전체와 B8~B11을 한국어 작업에 맞게 옮기고 고쳤다. 라이선스는 `LICENSE-landing-page-design` 참고.

랜딩 페이지는 홈페이지가 아니다. 홈페이지는 여러 목적을 받지만, 랜딩 페이지는 목적 하나를 이긴다:

**제안 하나 → 대상 하나 → 핵심 행동 하나.**

우선순위: 사용자 지시 > `DESIGN.md` > 이 문서 > frontend-design 기본값.

## 1. 사전 질문

디자인이나 문구 작업 전에 모은다. 빠진 것만, **한 번에 모아서** 묻는다. 하나씩 나눠 묻지 않는다.

**목적**
- 핵심 행동 하나는? (체험, 데모, 구매, 대기자 등록, 다운로드)
- 제안은 정확히 무엇인가? 방문자가 받는 것은?
- 무엇을 전환으로 보나? (클릭, 가입, 구매)

**대상과 맥락**
- 타깃 고객(ICP)은 누구인가?
- 그들이 풀려는 문제는?
- 지금 전환하지 않는 이유 세 가지
- 유입 경로: 광고, 검색, SNS, 이메일
- 방문자가 들어올 때 이미 알고 있는 것은?

**근거와 자료**
- 근거: 고객사 로고, 후기, 수치, 사례
- 스크린샷, 데모 영상, 제품 GIF
- 보증, 환불, 해지 조건

**제약**
- 브랜드 말투: 편한 말투 / 격식 있는 말투
- 디자인 방향 (`DESIGN.md`에 이미 있으면 그것을 따른다. 없으면 2단계 시안에서 정한다)
- 모바일 우선 여부

답을 못 받으면 합리적으로 가정하고, 그 가정을 한 줄로 밝힌 뒤 계속한다. 작업을 멈추지 않는다.

단, **근거와 자료**(고객사, 후기, 수치, 가격, 보증·환불 조건)는 가정으로 채우지 않는다. 사실 주장이기 때문이다. 받지 못한 근거는 9절의 "교체 자리"로 처리한다.

## 2. 페이지 구조

**첫 화면 (필수)**
1. 헤드라인: 결과 + 대상
2. 서브헤드: 어떻게 되는지, 구체적으로
3. 핵심 CTA: 분명한 동사 + 받는 것
4. 근거 하나: 로고 줄, 수치, 짧은 후기. 사용자가 준 실제 근거만 쓴다. 없으면 빼거나 9절의 교체 자리로 둔다
5. 히어로 시각물: 제품 스크린샷이나 영상, 또는 강한 일러스트

**중간 (설득)**
6. 문제 → 해결, 한 섹션
7. 장점 3~5개, 결과 중심
8. 사용 방법 3단계
9. 근거: 후기나 사례

**하단 (망설임 해소)**
10. FAQ 6~12개
11. 위험 줄이기: 무료 체험, 언제든 해지, 환불 보증
12. 마지막 CTA, 맨 위와 같은 것

## 3. 레이아웃 유형

하나를 고르고 **이유를 말한다**.

| 유형 | 언제 |
|---|---|
| **A. 기본형 (히어로 + 섹션)** | 히어로 스크린샷만 봐도 제품이 이해될 때. 가장 흔하다. |
| **B. 긴 스토리형** | 설명이 필요하고 의심을 풀어야 할 때. |
| **C. 최소 전환형** | 의도가 높은 유입(기존 사용자 대상 이메일 등)이거나 다운로드, 대기자 등록처럼 짧은 제안일 때. |
| **D. 비교형** | 검색 의도에 대안 비교("X vs Y", "~에 가장 좋은")가 있을 때. 보통 SEO 페이지와 짝을 이룬다. |

## 4. 전환 규칙

- **유입 경로와 메시지를 맞춘다.** 광고에서 오면 히어로에 광고 헤드라인을 그대로 받고, 같은 약속과 같은 시각 톤을 유지한다.
- **다음 행동을 분명하게.** 핵심 CTA는 하나. 첫 화면에 경쟁하는 CTA를 두지 않는다.
- **장점 먼저.** 기능은 제품이 하는 일이고, 장점은 그게 고객에게 뜻하는 것이다.
- **구체적으로.**
  - ❌ "시간을 절약하고 업무를 간소화하세요"
  - ✅ "주간 보고서 작성을 4시간에서 15분으로" (사용자가 준 수치일 때)
  - ✅ "지난주 거래 내역을 표 하나로 묶어 월요일 아침에 보내 줍니다" (수치가 없을 때: 숫자 대신 무엇을, 언제, 어떻게 하는지로 구체적으로)
  - 수치는 사용자가 준 것만 쓴다. 그럴듯한 수치를 만들어 넣지 않는다.
- **위험을 줄인다.** 실제로 제공하는 것 중 최소 하나: 무료 체험, 무료 요금제, 카드 등록 없음, 언제든 해지, 환불 보증. 제공하는지 모르면 사용자에게 묻고, 답이 없으면 넣지 않는다. 보증과 환불은 약속이라 지어내면 안 된다.
- **망설임은 각주가 아니라 섹션으로.** 부담이 큰 제안이면 FAQ를 앞으로 당긴다. 근거는 그 근거가 받치는 주장 바로 옆에 둔다.

## 5. 문구

**헤드라인 공식**
- "{고통} 없이 {결과}"
- "{대상}을 위한 {카테고리}"
- "{시간} 만에 {결과}"

**서브헤드**: 한두 문장. 무엇이고 누구를 위한 것인지 밝힌다.

**CTA**: 동사 + 받는 것. "더 알아보기", "제출" 같은 말은 쓰지 않는다. "무료로 시작하기", "데모 예약하기", "체크리스트 받기"처럼 쓴다.

**장점 목록**: 굵은 장점, 그다음 근거나 설명. 예: **빠른 반복** — 클릭 한 번으로 레이아웃 시안 세 개 생성.

과장어와 AI 말투 점검은 4단계 `antislop-copywriting`이 맡는다.

## 6. 작업 순서

섹션 하나씩, 이 순서로 만든다. 섹션마다 `frontend-design`을 적용한다.

1. 히어로
2. 장점
3. 사용 방법
4. 근거
5. FAQ
6. 마지막 CTA

수정할 때마다 페이지 전체를 다시 만들지 않는다. 섹션 단위로 해야 통제가 되고 변경 내용을 검토하기 쉽다.

## 7. SEO / AEO

- **검색에 노출하지 않는다**: 광고 전용 캠페인 페이지, 기간이 짧은 제안. `noindex`를 쓰거나 노출되지 않는 경로에 둔다.
- **노출한다**: 오래 쓰는 제안, 검색 의도와 약속이 맞는 페이지. 분명한 title과 meta description, 홈과 기능 페이지에서 오는 내부 링크, AI 검색(AEO)을 위한 평범한 질문·답 형식의 FAQ를 갖춘다. 맞으면 FAQ 스키마를 붙인다.

## 8. 흔한 실수

- 첫 화면에 CTA가 너무 많다
- 가치 제안이 모호하다: "간소화", "최적화"
- 결과 없이 기능만 길게 나열한다
- 근거가 맨 아래에 묻혀 있다
- 모바일에서 읽기가 깨진다
- 다음 행동이 분명하지 않다

## 9. 콘텐츠: 사실 주장과 예시 데이터

콘텐츠는 두 종류로 나눠 다룬다. 원본은 둘을 구분하지 않고 "그럴듯하게 지어내라"고 하지만, screendoro는 사실 주장을 지어내지 않는다 (`SKILL.md` 4단계 필수 항목, `design-setup.md` 3-5).

| 종류 | 예 | 처리 |
|---|---|---|
| **사실 주장** | 고객사 이름과 로고, 후기와 후기를 쓴 사람, 가격, 성과 수치(사용자 수, 절약 시간, 만족도), 수상, 언론 보도, 보증·환불 조건, 팀원 | 사용자가 준 자료만 쓴다. 없으면 교체 자리로 둔다 |
| **예시 데이터** | 제품 스크린샷이나 목업 **안**의 목록, 표, 그래프, 샘플 문서, 알림, 시스템 메시지 | 만들어 써도 된다. 아래 현실감 규칙을 따른다 |

방문자가 "이 회사가 주장하는 사실"로 읽을 수 있으면 사실 주장이다. 제품 화면 안에 들어 있어도 "누적 사용자 12,000명"처럼 회사를 자랑하는 숫자는 사실 주장이다.

### 9-1. 문구

- **문구를 직접 쓴다.** Lorem ipsum, "여기에 헤드라인" 금지. 제품 말투로 실제 문장을 쓴다. 헤드라인, 장점, 사용 방법, FAQ는 제품이 실제로 하는 일을 바탕으로 쓰는 것이라 사실 주장을 지어내는 것이 아니다. 단, 없는 기능을 쓰지 않는다.

### 9-2. 사실 주장이 없을 때: 교체 자리

- 근거 섹션(후기, 로고 줄, 수치)이 0-1단계 확정 구조에 있거나 사용자가 넣기로 했으면, 자리를 만들고 **교체 자리**로 표시한다.
  - 화면: 그 자리에 들어갈 자료를 짧게 적는다 (예: "고객 후기 2~3개가 들어갈 자리"). 실제 후기처럼 보이는 문장, 이름, 얼굴 사진을 넣지 않는다. 자리 표시는 `DESIGN.md`의 면 색과 글자 위계를 써서 레이아웃이 실제 자료가 들어온 모습과 같게 만든다.
  - 코드: `TODO(screendoro): 실제 자료로 교체: <무엇>` 주석을 단다. 나중에 검색으로 찾을 수 있게 형식을 지킨다.
  - 완료 보고: "실제 자료로 바꿀 것" 목록에 적는다.
- 확정 구조에 없고 AI가 넣으려던 근거 섹션이면, 교체 자리를 만들지 않고 **빼는 것**을 기본으로 한다. 넣는 게 낫다고 보면 사용자에게 알리고 판정을 받는다 (`draft-first.md` 6절 "나중에 생긴 차이").
- 가격표는 사용자가 가격을 줬을 때만 만든다. 구조만 필요하면 금액 자리를 교체 자리로 둔다.

### 9-3. 예시 데이터의 현실감

예시 데이터는 실제 사용자가 있는 실제 제품에서 나온 것처럼 읽혀야 한다.

- **사람.** 제품 화면 안의 이름은 대상과 지역에 맞게 구체적으로 짓는다. 홍길동, John Doe, 김철수 같은 이름은 쓰지 않는다. 얼굴 하나를 두 사람에게 쓰지 않는다.
- **회사와 상호.** 제품 화면 안의 거래처나 상호는 업종에 어울리게 짓는다. 물류 도구라면 일반 테크 스타트업이 아니라 물류 회사처럼 들려야 한다. 실존 회사 이름은 쓰지 않는다.
- **숫자.** 지나치게 딱 떨어지는 숫자를 피한다. 지표에는 소수점이나 끝자리가 홀수인 값을, 목록의 날짜는 서로 다르게.
- **시스템 메시지.** 확인 메시지는 차분하고 구체적으로("다나 님에게 청구서를 보냈습니다"). 오류는 무엇이 실패했고 무엇을 하면 되는지 말한다("업로드 실패. 파일이 20MB를 넘습니다."). 귀여운 감탄사, 느낌표 금지.

## 10. 상태

모든 인터랙티브 요소는 상태를 전부 갖춘다.

- **Hover**: 배경 변화, 살짝 커짐, 또는 이동
- **Active**: `scale(0.98)` 또는 `translateY(1px)`로 눌리는 느낌
- **Focus**: 보이는 포커스 링. 선택이 아니라 접근성 요구사항이다.
- **Loading**: 원형 스피너가 아니라 실제 레이아웃 모양의 스켈레톤
- **Empty**: 빈 패널이 아니라 짜임새 있는 "시작하기" 화면
- **Error**: 해당 위치에, 구체적으로. `window.alert()` 금지.

죽은 링크 금지. `#`로 가는 버튼은 링크를 연결하거나 비활성으로 보이게 한다. 내비게이션에 현재 페이지를 표시한다.

## 11. 출시 체크

자주 빠뜨려서 페이지가 미완성처럼 보이게 만드는 것들:

- 푸터의 개인정보처리방침, 이용약관 링크
- 브랜드에 맞춘 커스텀 404
- 이메일 형식과 필수 항목에 대한 클라이언트 쪽 폼 검증
- 키보드 사용자를 위한 본문 바로가기(skip link)
- 관할 지역에서 필요하면 쿠키 동의
- 브랜드 파비콘
- `<title>`, meta description, `og:image`, SNS 공유 태그
- 의미 있는 이미지마다 alt 텍스트
- 시맨틱 HTML: `<nav>`, `<main>`, `<article>`, `<aside>`, `<section>`
- 모든 페이지에서 돌아갈 길

## 12. 태그라인 등장 섹션 (권장)

원본에서는 필수지만 여기서는 **권장**이다. 모든 랜딩에 넣으면 결과물이 같은 모양으로 굳는다. 제품과 말투에 맞을 때만 넣고, 넣는 이유를 한 줄 남긴다.

- 히어로와 떨어진 곳에 두는 큰 글씨 섹션. 핵심 장점이나 태그라인을 두 줄 이상으로 쓴다. 일반적인 섹션 제목이 아니라 5절 말투로 쓴 문장이다.
- 크기는 `text-4xl`~`text-6xl`(또는 `DESIGN.md`의 해당 단계). 너비는 히어로처럼 제한하고 의미 단위로 줄을 끊는다.
- 애니메이션: 글자는 기본 글자색의 약 25~35% 불투명도로 시작한다. 스크롤해서 들어오면 단어가 읽는 순서대로 **하나씩** 원래 색으로 바뀐다. 블록 전체가 한 번에 바뀌지 않는다. `DESIGN.md`의 기본 곡선을 쓰고, linear는 쓰지 않는다.
- 단어별 `IntersectionObserver`나, `requestAnimationFrame`으로 조절한 스크롤 리스너 하나로 구현한다. 조절 없는 `window.addEventListener('scroll')`은 금지.
- `prefers-reduced-motion`이면 움직임 없이 바로 원래 색으로 보여 준다.

## 코드 전 결과물

랜딩을 새로 만들 때 코드보다 먼저 이것들을 순서대로 내놓는다.

1. **페이지 개요**: 섹션과 순서
2. **히어로 문구**: 헤드라인, 서브헤드, CTA, 근거 한 줄
3. **장점**: 결과 중심 3~5개
4. **사용 방법**: 3단계
5. **FAQ**: 질문과 답 6~12개
6. **SEO / AEO**: 노출 여부 권고, 노출하면 title과 meta
7. **레이아웃 선택**: A, B, C, D 중 하나와 이유

그다음 6절 순서대로 섹션별로 만든다.

## 체크리스트 (4단계에서 antislop과 함께 실행)

**전략**
- [ ] 제안 하나, 대상 하나, 핵심 행동 하나
- [ ] 첫 화면에 경쟁하는 CTA 없음
- [ ] 모호한 동사 대신 구체적인 표현 (수치는 사용자가 준 것만)
- [ ] 실제로 제공하는 위험 줄이기 장치가 있으면 최소 하나 드러남 (지어낸 보증·환불 없음)
- [ ] 근거가 그 근거가 받치는 주장 옆에 있음
- [ ] 레이아웃 유형을 이유와 함께 고름

**콘텐츠와 출시**
- [ ] 실제 문구. 후기·로고·가격·성과 수치는 사용자가 준 자료이거나, 교체 자리와 `TODO(screendoro)` 주석으로 표시됨
- [ ] 제품 화면 안의 예시 데이터는 그럴듯하고, 회사의 사실 주장으로 읽히지 않음
- [ ] hover, active, focus, loading, empty, error 상태 모두 있음
- [ ] 죽은 링크 없음, 현재 내비게이션 항목 표시
- [ ] 404, 법적 고지 링크, 폼 검증, 파비콘, 메타 태그, alt 텍스트
- [ ] 태그라인 섹션을 넣었다면 이유가 있고, 단어가 하나씩 바뀌며, reduced-motion을 지원함
