# Screendoro

프론트엔드 작업은 아래 단계를 **이 순서대로** 반드시 지킨다. 단계를 건너뛰거나 순서를 바꾸지 않는다. 1단계만 예외로, 랜딩·마케팅 페이지일 때만 수행한다. 0-1단계는 사용자가 명시적으로 건너뛰겠다고 할 때만 건너뛴다.

우선순위: 사용자 지시 > `references/house-rules.md`(고정 규칙) > 프로젝트 `DESIGN.md` > 다른 `references/` 문서 > `frontend-design` 기본값 > Astryx 기본값. 0-1단계의 확정 구조는 사용자 지시로 본다.

고정 규칙: `references/house-rules.md`는 모든 프로젝트에 적용하는 사용자 규칙이다(경기천년체, 둥근 버튼, 이중 테두리 금지, 불필요한 밑줄·요소 금지). 2·3단계에서 반영하고 4단계에서 위반을 찾아 고친다. 폰트는 기존 폰트가 있는 프로젝트, 한글 없는 사이트, 작업형 화면의 작은 글자에서 사용자가 예외를 고를 수 있다 (`house-rules.md` 1-1절).

컴포넌트 라이브러리(선택): 마커의 `componentLib`이 `"astryx"`인 프로젝트에서만 `references/astryx.md`를 읽고 따른다. Astryx는 부품과 테마 엔진만 맡고, 단계 순서와 고정 규칙은 바뀌지 않는다. 그 외 프로젝트에서는 이 문서를 읽지 않는다.

일관성: 같은 요청에도 화면이 매번 다르게 나오는 "뽑기"를 줄이려고, 탐색(2단계 시안)은 여러 개를 만들어 고르고 생산(3단계 화면)은 고른 결정을 굳힌 코드 키트와 레이아웃 문법으로 조립한다. 절차는 `references/consistency.md`에 있고, 각 단계가 읽을 절을 지정한다.

적용 범위: 새 화면·페이지를 만들거나 화면을 크게 재구성하는 작업에만 쓴다. "크게 재구성"은 섹션 구성이나 순서, 화면 배치가 바뀌는 것이다. 문구, 색·간격, 버그 수정, 컴포넌트 하나 손보기 같은 작은 변경은 이 워크플로 없이 `DESIGN.md`와 고정 규칙에 맞춰 바로 고친다.

만드는 파일: 아래 파일을 만든다. 처음 만들 때 git에 올릴지는 사용자가 정할 일이라고 한 줄로 알리고, 묻지 않고 `.gitignore`를 고치지 않는다. 흔한 선택은 결정 기록(표의 앞 네 줄)은 올리고, 작업 산출물(`screendoro-mocks/`, `screendoro-render/`)은 올리지 않는 것이다.

| 파일 | 내용 |
|---|---|
| `DESIGN.md` (프로젝트 루트) | 디자인 결정과 토큰 원본 |
| `.claude/screendoro.json` | 마커 |
| `.claude/screendoro-draft.md`, `-refs.md`, `-feedback.md` | 초안과 판정, 레퍼런스 노트, 거절 피드백 |
| `.claude/screendoro-approved/` | 승인 캡처 (비교 기준) |
| `.claude/screendoro-mocks/` | 와이어프레임, 시안, 레퍼런스 보드, 키트 카탈로그 |
| `.claude/screendoro-render/` | Playwright 캡처와 결과 JSON |
| `~/.claude/screendoro-taste.md` | 프로젝트를 넘는 취향 (사용자 허락을 받고만 쓴다) |

스킬 로드 원칙: 한 세션에서 이미 불러온 스킬(`frontend-design`, `antislop` 계열 등)과 이미 읽은 `references/` 문서는 다시 불러오지 않는다. 컨텍스트에 남아 있는 지침을 그대로 따른다. **예외**: 대화가 요약돼 그 지침의 본문이 컨텍스트에 더는 보이지 않으면(요약에 "불러왔다"는 기록만 남은 경우 포함) 다시 불러온다. 본문 없이 기억으로 따르지 않는다.

스킬 이름: 이 문서는 짧은 이름으로 적는다. Skill 도구로 부를 때는 사용 가능한 스킬 목록에 실제로 있는 이름을 쓴다. 플러그인으로 설치됐으면 앞에 플러그인 이름이 붙는다.

| 이 문서의 이름 | 플러그인 설치 시 이름 |
|---|---|
| `frontend-design:frontend-design` | `frontend-design:frontend-design` (같음) |
| `antislop`, `antislop-ui` 등 | `antislop:antislop`, `antislop:antislop-ui` 등 |
| `web-quality-audit` | `web-quality-skills:web-quality-audit` |

목록에 둘 다 있으면 플러그인 쪽을 쓴다. 목록에 없는 스킬은 지어내지 말고, 빠진 스킬과 건너뛴 단계를 완료 보고에 적는다.

## 0. 시작 전: 현재 프로젝트 상태 확인

프로젝트 루트에서 `.claude/screendoro.json` 마커 파일을 확인한다.

- 파일이 있고 `"setupDone": true` 이면 → 2단계를 건너뛴다. 예전 버전이 기록한 `"impeccableDone": true`도 같은 뜻으로 본다.
- 파일이 없으면 → 이 프로젝트에 이미 프론트엔드 환경이 있는지 본다 (`package.json`의 프론트엔드 의존성, `src/` 아래 컴포넌트, `index.html`, `DESIGN.md`, 디자인 토큰 파일 등).
  - 프론트엔드 환경이 **없다** → 2단계를 수행한다.
  - 프론트엔드 환경이 **이미 있다** → 2단계(시안으로 새 방향 정하기)를 그대로 하면 기존 화면 위에 새 스타일을 얹는 리디자인이 된다. AskUserQuestion으로 한 번 묻는다.
    - **기존 스타일 따르기** (기본값): 2단계를 건너뛴다. `consistency.md` 7절대로 기존 컴포넌트와 화면을 키트로 보고 조립한다. `DESIGN.md`가 없으면 기존 화면에서 실제로 쓰는 값만 뽑아 `DESIGN.md`를 만들고 값마다 `[기존]`을 단다 (`design-setup.md` 5-3절). 마커에 `"setupDone": true, "setupMode": "existing"`을 적는다.
    - **리디자인**: 2단계를 수행한다. 바뀌는 범위(새 화면만 / 앱 전체)를 먼저 정한다.
    - 기존 폰트가 경기천년체가 아니면 `house-rules.md` 1-1절 폰트 예외도 같은 질문 묶음에서 묻는다.

마커의 `kitPath`로 코드 키트가 있는지 본다. 마커는 있는데 `kitPath`가 없으면 `consistency.md` 7절대로 기존 컴포넌트와 화면을 키트로 본다.

사용자 취향 파일 `~/.claude/screendoro-taste.md`가 있으면 읽는다. 프로젝트의 `.claude/screendoro-feedback.md`가 있으면 그것도 읽는다 (`consistency.md` 4절). 둘 다 이전에 사용자가 거절한 이유이므로 같은 처리를 다시 내지 않는다.

그다음 **작업 유형**을 판별한다.

- 랜딩 페이지, 마케팅 사이트, 제품 소개·가입 유도 페이지 → **랜딩 작업**. 1단계를 수행한다.
- 대시보드, 앱 화면, 설정, 일반 컴포넌트 등 그 외 → 1단계를 건너뛴다.
- 애매하면 사용자에게 한 번 묻는다.

마지막으로 **컴포넌트 라이브러리**를 판별한다. 마커에 `componentLib`이 있으면 그 값을 따르고, 없으면 `references/astryx.md` 1절의 표대로 정한다.

- 2단계를 수행하는 프로젝트(최초 구성)이면서 React 19 이상이거나 프레임워크를 아직 정하지 않았을 때만 Astryx를 쓸지 한 번 묻는다. 기본값은 **쓰지 않음**이다.
- 그 외에는 묻지 않는다. `package.json`에 `@astryxdesign/core`가 있으면 Astryx 프로젝트로 보고, 나머지는 쓰지 않는 것으로 본다.

## 0-1. 초안 맞추기 — `references/draft-first.md` (새 화면마다)

화면의 구조는 사용자가 먼저 생각한다. 0단계 판별이 끝나면 시안, 랜딩 전략, 화면 코드보다 먼저 `references/draft-first.md`를 읽고 수행한다. 마커가 있는 프로젝트에서도 새 화면마다 한다.

1. **초안 받기**: 구조나 디자인 방향을 제안하기 전에 사용자의 초안을 받는다. 요소와 순서, 가장 중요한 것 하나, 레퍼런스(URL이나 스크린샷)와 가져오고 싶은 점. 자유 서술로 받고, 예시나 선택지를 먼저 내지 않는다. 랜딩 작업이면 1단계 사전 질문 중 빠진 것도 함께 묻는다.
2. **그대로 기록**: `.claude/screendoro-draft.md`에 사용자의 말 그대로 적는다. 정하지 않은 항목은 빈칸으로 둔다.
3. **레퍼런스 읽기**: 사용자가 준 레퍼런스를 `references/design-reference.md`의 D·E로 읽는다 (B·C는 건너뛴다).
4. **구조안**: 글로 된 구조안을 낸다. 차이 표시 없이 보여주고, 초안과 다른 부분을 짚어 달라고 요청한다.
5. **차이 지적과 공개**: 사용자가 먼저 지적한다. 그다음 사용자가 짚지 않은 차이(바꿈, 뺌, 채움)를 이유와 함께 모두 공개한다.
6. **판정**: 차이마다 초안대로 / AI안 / 절충을 받아 확정 구조를 기록한다. 판정이 끝나기 전에는 시안도 코드도 만들지 않는다.

- 사용자가 "초안 없이"라고 명시하면 건너뛰고 기존 흐름대로 간다. AI가 먼저 건너뛰자고 권하지 않는다.
- **간단 모드**: 키트가 있는 프로젝트의 작업형 하위 화면(설정, 목록, 상세, 폼 등)이면 초안 요청을 한 줄로 줄이고, 구조안과 차이 공개를 한 메시지에 낸다 (`draft-first.md` 7절). 초안을 먼저 받는 것과 판정 전에 만들지 않는 것은 그대로다.
- 이후 단계는 확정 구조를 따른다. 다르게 해야 할 이유가 생기면 바꾸기 전에 사용자에게 알리고 판정을 받는다.

## 1. 랜딩 전략 — `references/landing-strategy.md` (랜딩 작업일 때만)

랜딩 작업이면 화면 코드를 쓰기 전에:

1. `references/landing-strategy.md`를 읽는다.
2. 1절 사전 질문 중 빠진 것만 **한 번에 모아서** 묻는다. 답이 없으면 가정을 한 줄로 밝히고 계속한다.
3. 코드보다 먼저 "코드 전 결과물" 7가지(개요, 히어로 문구, 장점, 사용 방법, FAQ, SEO/AEO, 레이아웃 선택과 이유)를 내놓는다.
4. 3단계에서 6절 순서(히어로 → 장점 → 사용 방법 → 근거 → FAQ → 마지막 CTA)대로 섹션 하나씩 만든다.
5. 0-1단계의 확정 구조가 있으면 섹션 구성과 순서는 확정 구조를 따른다. 6절 순서와 다르면 확정 구조가 이긴다. 확정 구조에 없는 섹션이 필요하다고 판단하면 넣기 전에 사용자에게 알리고 판정을 받는다.

이 문서의 시각 값은 `DESIGN.md`보다 우선하지 않는다. 최초 구성 프로젝트라 `DESIGN.md`가 아직 없으면 레이아웃 선택은 구조 수준에서만 하고, 색·폰트 같은 시각 값은 2단계 시안에서 정한다.

## 2. 최초 환경 구성 — `references/design-setup.md` (프로젝트당 1회)

- 프로젝트에서 프론트엔드 환경을 **처음** 작성할 때만 `references/design-setup.md`를 읽고 그 순서대로 환경(디자인 방향, `DESIGN.md`, 토큰, 기본 구조)을 구성한다.
- 시안을 그리기 전에 `frontend-design:frontend-design` 스킬을 불러온다. 이 세션에서 이미 불러왔으면 다시 불러오지 않고, 3단계에서도 다시 불러오지 않는다.
- 시작 전에 `references/house-rules.md`를 읽는다. 모든 시안과 `DESIGN.md`의 폰트는 경기천년체(1-1절 예외를 고른 프로젝트면 그 폰트), 버튼 반경은 8px 이상으로 정하고, 이중 테두리와 불필요한 밑줄·요소는 시안에도 넣지 않는다. 시안끼리는 폰트가 같으므로 레이아웃, 색, 글자 크기·굵기 대비, 분위기로 차이를 낸다.
- 시안 방향을 고르기 전에 `references/slop-tells.md`를 읽는다 (이 세션에서 이미 읽었으면 생략). 사용자가 고르지 않았는데 시안 방향이 1절 다섯 유형 중 하나에 해당하면 후보에서 빼거나 한 축 이상을 제품 주제 쪽으로 옮긴다.
- 디자인 방향을 정할 때, 사용자가 방향을 따로 정하지 않았다면 `references/landing-visual-preset.md`를 **선택지 중 하나로** 제시한다. 강제하지 않는다.
  - 고르면 그 파일의 "쓰는 법"대로 값을 `DESIGN.md`에 **값마다 이유와 함께** 옮겨 적고 `[승인: 프리셋]`을 단다.
  - 프리셋의 폰트 규칙 대신 고정 규칙의 경기천년체를 쓴다.

### 2-1. 시안 선택 (2단계 안에서, 프로젝트당 1회)

디자인 방향을 `DESIGN.md`와 토큰에 확정하기 **전에**, 사용자가 직접 눈으로 보고 고르게 한다. 시안은 이미지가 아니라 HTML로 직접 그린다.

0. **시안 방식 선택**: 시안을 그리기 전에 AskUserQuestion으로 한 번 묻는다. 레퍼런스는 참고 수단이지 필수가 아니다.

   | 방식 | 레퍼런스 수집 | 시안 수 | 파일 |
   |---|---|---|---|
   | **레퍼런스 없이** (기본값) | 안 함 | 자체 방향 3개 | `option-a~c.html` |
   | **레퍼런스 기반** | 함 | 레퍼런스 기반 3개 | `option-a~c.html` |
   | **둘 다 보여주기** | 함 | 레퍼런스 기반 2개 + 자체 방향 2개 | `option-r1`, `option-r2`, `option-f1`, `option-f2` |
   | **내 초안 기반** | 사용자가 준 레퍼런스만 | 확정 구조를 지킨 3개 | `option-a~c.html` |

   - 0-1단계를 수행했으면(건너뛰지 않았으면) 묻지 않고 **내 초안 기반**으로 한다. 0-1단계에서 갤러리 수집을 골랐으면 그 레퍼런스도 근거로 쓴다.
   - 답이 없거나 "알아서"라고 하면 **레퍼런스 없이**로 진행하고, 그렇게 했다고 한 줄로 알린다.
   - 사용자가 처음부터 레퍼런스 URL을 줬거나 "레퍼런스 참고해서"라고 했으면 묻지 않고 **레퍼런스 기반**으로 한다.
   - 레퍼런스를 쓰는 방식이면 `references/design-reference.md`를 읽고 A~E를 수행한다. 갤러리 후보 6~9개를 보드로 보여주고, 사용자가 2~4개를 확정하면 패턴을 뽑아 `.claude/screendoro-refs.md`에 정리한다.

1. **구조 와이어프레임**: `references/consistency.md` 1절대로 대표 화면 **전체**의 구조(섹션 구성과 순서, 섹션별 내용과 정보량, 첫 화면 범위)를 회색 상자 와이어프레임으로 그려 보여 주고 확정한다. 배치·색·타이포·분위기는 정하지 않는다. 이후 모든 시안은 이 구성을 지킨다.

2. 방식에 맞게 서로 **확연히 다른** 시안 방향을 고른다.
   - **자체 방향**: `design-setup.md` 3절로 만든 방향에서 고른다. 레퍼런스 노트를 보지 않는다.
   - **레퍼런스 기반**: 레퍼런스 노트의 "시안에 쓸 조합"을 바탕으로 고른다. 각 시안은 레퍼런스 2개 이상의 패턴을 조합하고, 비교 페이지 설명에 근거 번호를 단다.
   - **둘 다**: 자체 방향 2개는 레퍼런스 기반 2개와도 겹치지 않아야 한다. 같은 방향이 양쪽에 나오면 비교가 안 된다.
   - **내 초안 기반**: 모든 시안이 확정 구조(요소와 순서)를 지킨다. 시안끼리는 배치 방식(그리드, 정렬, 비율), 색, 타이포, 분위기로 차이를 낸다. 레퍼런스가 1개뿐이면 "2개 이상 조합" 규칙을 적용하지 않고, 사용자가 가져오고 싶다고 한 점만 가져온다.
   - 레이아웃 구조, 색, 타이포, 분위기가 모두 달라야 한다. 확정 구조와 와이어프레임의 섹션 구성은 같게 두고 나머지로 차이를 낸다. 색만 바꾼 변형은 다른 시안으로 치지 않는다. 사용자가 프리셋을 원하면 그중 하나를 `landing-visual-preset.md` 기반 시안으로 채운다.
3. 각 시안을 프로젝트 대표 화면의 **첫 화면 + 대표 섹션 1~2개** 수준의 정적 HTML로 만든다. 대표 섹션은 와이어프레임에서 방향 차이가 가장 잘 드러나는 섹션을 고르고, 모든 시안이 같은 섹션을 그린다 (`consistency.md` 1절). 실제 제품명과 실제 내용을 쓰고, 가격·고객사·수치 같은 사실 주장은 지어내지 않는다. 랜딩 작업이면 1단계에서 정한 히어로 문구와 섹션 순서를 시안에 쓴다.
   - 각 시안을 다 그린 뒤 `slop-tells.md` 3절 질문으로 한 번 점검한다. 걸리는 곳은 지우기만 하지 말고 그 시안의 방향에서 나온 처리로 바꾼다. 같은 처리(같은 카드 그리드, 같은 히어로 배치)가 여러 시안에 반복되면 그 시안들은 서로 다른 방향이 아니다.
   - 파일: 0번 표의 파일 이름을 `.claude/screendoro-mocks/` 아래에 만든다.
   - 비교 페이지 `.claude/screendoro-mocks/index.html`에 시안을 탭이나 나란히 보기로 모으고, 각 시안 위에 이름과 한 줄 설명(방향, 장점, 위험)을 단다. 점검 뒤에도 남긴 처리 중 `slop-tells.md` 1·2절에 걸리는 것이 있으면 "위험"에 이름을 밝힌다. 사용자가 그 시안을 고르면 그 처리도 알고 고른 것이 된다. **둘 다** 방식이면 "레퍼런스 기반"과 "자체 방향" 두 묶음으로 나눠 보여주고, 레퍼런스 기반 시안에는 근거 번호를 단다.
4. 비교 페이지를 브라우저 패널에 띄워 사용자에게 보여준다.
5. AskUserQuestion 도구로 시안 하나를 고르게 한다. 사용자는 "A의 레이아웃에 B의 색" 같은 조합(레퍼런스 기반과 자체 방향을 섞는 것도 포함)이나 다시 그리기를 요청할 수 있다. 방식을 바꿔 달라고 하면 0번부터 다시 한다.
   - **다시 그리기나 거절**이면 `consistency.md` 4절대로 어느 축(배치 / 색 / 타이포 / 밀도·여백 / 분위기)이 문제인지 먼저 묻고 `.claude/screendoro-feedback.md`에 기록한다. 고른 축만 바꾸고 나머지는 유지해서 다시 만든다. 방향 전체가 아니라고 하면 이미 보여준 방향은 빼고 같은 방식, 같은 개수로 새로 만든다.
6. 고른 시안의 값(색, 폰트, 간격, 레이아웃 구조)을 `DESIGN.md`에 **값마다 이유와 승인 표시를 붙여** 기록하고 (`design-setup.md` 5-3절. 시안에 보였던 값만 `[승인: 시안 X]`, 시안에 없던 값은 `[AI]`) 토큰으로 옮긴 뒤 환경 구성을 마친다. 그다음 `design-setup.md` 6절대로 기본 구조를 만든다.
   - `DESIGN.md`에 **레이아웃 문법**(그리드, 섹션 리듬, 섹션 유형, 시그니처 규격, 밀도)도 적는다 (`consistency.md` 2절).
   - 이어서 **코드 키트**를 최소한으로 만든다: 기본 부품과 시그니처, 시안에 실제로 그린 섹션의 틀만. 나머지 섹션 틀은 3단계에서 처음 쓸 때 만든다. `house-check.js`와 `design-check.js`로 카탈로그를 점검한다 (`consistency.md` 3-1절).
   - 고른 시안의 캡처를 `.claude/screendoro-approved/`에 첫 승인 기준으로 저장한다 (`consistency.md` 5-1절).
7. **Astryx 프로젝트면** (0단계에서 `componentLib`이 `"astryx"`로 정해졌으면) 시안을 고른 뒤 `references/astryx.md` 2~3절을 수행한다. Astryx를 설치해 연결하고, `DESIGN.md` 값과 고정 규칙(경기천년체, 버튼 반경)을 Astryx 테마 토큰으로 옮긴다. 시안 자체는 Astryx 없이 정적 HTML로 그린다.

- 구성이 끝나면 프로젝트 루트에 마커를 기록한다. 프리셋을 고르지 않았으면 `visualPreset`은 빼거나 `null`로 둔다. `mockMode`에는 고른 방식(`none` / `reference` / `both` / `draft`)을, `mockChoice`에는 고른 시안과 한 줄 요약을, `references`에는 확정한 레퍼런스 URL을 적는다. 레퍼런스를 쓰지 않았거나 레퍼런스 기반이 아닌 시안을 골랐으면 `references`와 `refsNote`는 빼도 된다. `surfaceMode`에는 `design-setup.md` 2절에서 정한 화면 성격을 적는다. `componentLib`에는 `"astryx"` 또는 `"none"`을 적고, Astryx를 쓰면 `astryxTheme`에 바탕으로 삼은 테마 이름을 적는다. `kitPath`에는 코드 키트 위치를 적는다.

  ```json
  // .claude/screendoro.json
  { "setupDone": true, "setupMode": "new", "date": "YYYY-MM-DD", "surfaceMode": "persuade", "visualPreset": "landing-visual-preset", "mockMode": "both", "mockChoice": "B - <고른 시안의 배치 · 바탕 · 글자 대비 한 줄>", "references": ["https://..."], "refsNote": ".claude/screendoro-refs.md", "componentLib": "astryx", "astryxTheme": "neutral", "kitPath": "src/design/", "fontFiles": ["public/fonts/..."], "fontException": null }
  ```

  예시의 값은 형식만 보여 준다. 이 문서와 `references/`에 나오는 예시 소재(지하철 노선도, 녹회색 바탕 등)를 시안 방향으로 가져다 쓰지 않는다. 예시가 반복되면 그것이 새 기본값이 된다.

- 이후 이 프로젝트의 어떤 화면 작업에서도 2단계를 **다시 하지 않는다**. 사용자가 리디자인을 요청할 때만 다시 한다.

## 3. 화면 작성 — `frontend-design:frontend-design` (세션당 1회 로드)

- 화면(페이지, 컴포넌트, 레이아웃 등)을 작성하기 전에 `frontend-design:frontend-design` 스킬을 Skill 도구로 불러온다. 이 세션에서 이미 불러왔으면 다시 불러오지 않는다.
- `frontend-design`을 불러온 직후 `references/house-rules.md` 1~4절을 읽는다 (이 세션에서 이미 읽었으면 생략). `frontend-design` 지침과 충돌하면 고정 규칙을 따른다.
  - 글씨 폰트는 경기천년체 (제목·버튼은 경기천년제목, 본문은 경기천년바탕). 마커에 `fontException`이 있으면 그 폰트
  - 버튼은 모서리가 둥근 모양 (반경 8px 이상)
  - 이중 테두리 금지
  - 불필요한 밑줄과 장식 요소 금지
- 이어서 `references/slop-tells.md`를 읽는다 (이 세션에서 이미 읽었으면 생략). 4단계에서 잡을 슬롭을 만들기 전에 피하려는 것이다.
- 화면마다 아래 3-1 → 3-4 순서로 만든다. 2단계에서 정한 디자인 방향·토큰(`DESIGN.md`)이 있으면 그것과 일관되게 맞춘다.

### 3-1. 계획 (코드 전)

화면마다 짧은 계획을 쓴다. 사용자에게 몇 줄로 보여 주고, 승인을 기다리지 않고 진행한다.

- **시그니처 하나**: 이 화면에서 기억에 남을 요소 하나와, 그것이 `DESIGN.md`의 방향(세계)에서 어떻게 나오는지 한 줄
- **섹션별 처리**: 섹션(또는 화면 영역)마다 `DESIGN.md` 레이아웃 문법의 **섹션 유형**을 고르고 담을 내용을 적는다 (`섹션 이름 → 유형 → 내용`). 맞는 유형이 없을 때만 새 유형을 만들고 이유를 한 줄 적는다 (`consistency.md` 3-2절). 레이아웃 문법이 없는 프로젝트면 배치, 정렬, 밀도를 한 줄씩 적는다. ASCII 와이어프레임을 써도 된다. 섹션끼리 리듬이 달라야 한다. 모든 섹션이 "가운데 제목 + 부제 + 같은 그리드"면 다시 짠다.
- **랜딩 작업이면** 1단계의 섹션은 담을 정보다. 생김새는 여기서 정한다. "장점 3~5개"가 같은 카드 3개일 필요는 없고, "사용 방법 3단계"가 아이콘 + 1·2·3일 필요도 없다.
- 섹션 하나씩 구현하더라도 계획은 페이지 전체를 먼저 짠다. 섹션을 따로 설계하면 같은 띠가 반복된다.

### 3-2. 뻔함 점검 (코드 전)

계획의 줄마다 `slop-tells.md` 3절 질문을 던진다. 특히 "비슷한 다른 제품의 화면을 요청받았어도 똑같이 계획했을까?" 그렇다면 그 줄을 고치고, 무엇을 왜 바꿨는지 한 줄로 알린다.

- 0-1단계 확정 구조의 요소와 순서, 사용자가 정한 것은 바꾸지 않는다. 생김새만 바꾼다.
- `slop-tells.md` 2절 징후와 겹치는 줄도 고친다.

### 3-3. 구현 (조립)

고친 계획대로 **코드 키트의 부품과 섹션 틀을 조립해서** 구현한다 (`consistency.md` 3-2절).

- 키트 부품을 화면마다 다시 스타일링하지 않는다. 변형이 필요하면 키트 부품에 변형을 더한다.
- 새로 만든 섹션 틀이나 부품은 키트와 `DESIGN.md`에 `[AI]`로 더하고, 완료 보고에 "승인 대기 키트"로 적는다.
- 키트 부품 자체를 고쳐야 하면 모든 화면이 바뀌므로 고치기 전에 사용자에게 알린다.
- 색과 치수는 토큰만 쓴다. 토큰에 없는 값이 필요하면 하드코딩하지 말고 토큰으로 더한다.

### 3-4. 자기 비평 (1회)

구현한 화면을 한 번 보고 고친다. 4단계 검증과는 별개다.

- 화면을 띄울 수 있으면 데스크톱 폭 캡처를 본다 (랜딩이면 첫 화면과 페이지 전체). 띄우는 방법은 `render-check.md` 1절을 따른다. 브라우저 패널이 없으면 `render-pw.cjs --widths 1280`으로 캡처와 `design-check.js` 결과를 한 번에 얻는다.
- `slop-tells.md` 3절 질문으로 보고, 가장 뻔한 곳 1~3곳을 다시 설계한다. 지우기만 하지 않고 방향에서 나온 처리로 바꾼다.
- 계획한 시그니처가 실제 화면에서 보이는지 확인한다. 묻혔으면 살리고, 눈에 띄는 요소가 여러 개면 하나만 남긴다.
- `references/design-check.js`를 데스크톱 폭에서 한 번 실행해 토큰 밖 값과 구조 반복을 확인한다 (읽는 법은 `consistency.md` 6절).
- `.claude/screendoro-approved/`의 승인 캡처 1~2장과 나란히 보고 같은 제품처럼 보이는지 확인한다 (`consistency.md` 5-2절).
- 띄울 수 없으면 코드를 기준으로 같은 점검을 하고, 완료 보고에 "자기 비평: 코드 기준"이라고 적는다.
- 1회만 한다. 남은 문제는 4단계에서 다룬다.
- 사용자가 화면을 거절하거나 다시 만들어 달라고 하면 `consistency.md` 4절대로 문제인 축을 묻고 그 축만 바꾼다.

### 3단계 공통

- **Astryx 프로젝트면** 화면 코드를 쓰기 전에 `references/astryx.md` 4~5절을 읽는다 (이 세션에서 이미 읽었으면 생략). 부품은 CLI로 조회해서 Astryx 것을 쓰고, 색과 치수는 테마 토큰을 쓴다. Astryx가 프로젝트에 써 넣은 안내와 이 문서가 다르면 이 문서를 따른다.
- 랜딩 작업이면 1단계 결과물과 섹션 순서를 따라 섹션 단위로 구현한다.
- 0-1단계의 확정 구조가 있으면 그대로 구현한다. 구현하다가 다르게 해야 할 이유가 생기면 바꾸기 전에 사용자에게 알리고 판정을 받아 `.claude/screendoro-draft.md`에 이어 적는다.
- 여러 화면을 만들 때도 모든 화면에 이 지침을 적용한다 (스킬은 한 번만 불러온다).
- **레퍼런스 요청 시**: 사용자가 레퍼런스 URL을 주거나 레퍼런스를 찾아 달라고 하면, 화면 코드 전에 `references/design-reference.md`를 읽고 수행한다. URL을 받았으면 B·C를 건너뛰고 D부터 한다. 뽑은 패턴은 `DESIGN.md`와 충돌하지 않는 범위에서만 쓰고, 충돌하면 어느 쪽을 따를지 사용자에게 묻는다. 노트는 `.claude/screendoro-refs.md`에 이어 쓴다.

## 4. 최종 검증 — `antislop` (구현이 모두 끝난 뒤)

구현이 **최종적으로 모두** 끝나면, 완료 보고 전에:

1. `antislop` 코어 스킬을 불러온다 (이 세션에서 이미 불러왔으면 생략).
2. 하위 스킬은 작업의 **주된 성격에 맞는 1개만** 불러온다. 두 번째 하위 스킬은 그 영역이 작업의 큰 비중을 차지할 때만 추가한다 (예: 랜딩은 `antislop-ui` + `antislop-copywriting`).
   - UI/시각 요소(색, 레이아웃, 컴포넌트, 모션) → `antislop-ui`
   - 문구(헤드라인, CTA, 안내 문구) → `antislop-copywriting`
   - 반응형/모바일 레이아웃 → `antislop-layoutmobile`
   - 대비·키보드·포커스·상태 등 접근성 → `antislop-human`
   - 코드 주석 정리 → `antislop-code`
3. **고정 규칙 점검**: `references/house-rules.md` 5절 절차를 수행한다. 하위 스킬을 무엇으로 골랐든 항상 한다.
   - 이중 테두리를 적용했는지 확인하고, 있으면 한 겹만 남기고 지운다.
   - 불필요한 밑줄과 요소를 적용했는지 확인하고, 있으면 삭제한다. 지운 자리는 `house-rules.md` 4-1절 표의 처리로 채운다.
   - 경기천년체와 둥근 버튼이 적용됐는지 확인한다.
   - 그 외 AI 슬롭 패턴은 `antislop` 코어가 꼽는 패턴 전체로 화면 전체를 검사한다. 하위 스킬 영역 밖의 패턴도 빠뜨리지 않는다.
   - 렌더링 검증 때 폭마다 `references/house-check.js`와 `references/design-check.js`도 실행한다. `design-check.js` 결과의 등급은 `consistency.md` 6절 표를 따른다.
   - 승인 캡처와 비교해 이유 없이 달라진 곳을 찾는다 (`consistency.md` 5-2절).
   - 랜딩 작업이면 `references/landing-strategy.md` 끝의 체크리스트도 함께 돌린다. 마커에 `visualPreset`이 있으면 `references/landing-visual-preset.md` 끝의 체크리스트도 돌린다.
   - Astryx 프로젝트면 `references/astryx.md` 6절과 끝의 체크리스트도 함께 돌린다. Astryx 컴포넌트에서 나온 고정 규칙 위반도 필수 항목이고, 테마 토큰 → `className` → `swizzle`(사용자에게 물은 뒤) 순으로 고친다.
4. **초안 대조**: 0-1단계를 수행했으면 만든 화면을 `.claude/screendoro-draft.md`의 확정 구조와 항목별로 대조한다. 판정 없이 달라진 곳을 찾는다.
5. **렌더링 검증**: `references/render-check.md`를 읽고 그대로 수행한다. 만든 화면을 실제로 띄워 모바일·태블릿·데스크톱 폭에서 캡처하고, 가로 스크롤, 콘솔 오류, 실패한 요청, 핵심 상호작용을 확인한다.
   - 랜딩·공개 페이지(검색 노출이나 첫 로딩 속도가 중요한 페이지)면 `web-quality-audit` 스킬을 불러와 성능·SEO·best practices 기준도 함께 적용한다. 로그인 뒤 앱 화면에는 불러오지 않는다.
   - `web-quality-audit`가 링크하는 하위 스킬(`accessibility`, `performance` 등)은 따로 불러오지 않는다. 필요한 부분만 그 파일을 읽는다. 접근성 판단은 `antislop-human`과 중복되므로, 둘이 다르면 더 엄격한 쪽을 따른다.
6. 작성한 화면 전체에서 슬롭 패턴, 체크리스트 미충족 항목, 초안 대조 결과, 렌더링 검증 결과를 모아 두 등급으로 나눠 정리한다.
   - **필수**: 고정 규칙 위반(이중 테두리, 불필요한 밑줄·요소, 경기천년체 아님, 각진 버튼), 판정 없이 확정 구조와 달라진 곳, 토큰 밖 값(`design-check.js`), 레이아웃 문법 위반, 대비·접근성 위반, 깨진 레이아웃·가로 스크롤, 동작 오류, 지어낸 사실 주장, `DESIGN.md` 위반, 이 작업에서 생긴 콘솔 오류, 실패한 리소스 요청(깨진 이미지·폰트), CLS 0.1 초과
   - **권장**: 취향·스타일 차원의 슬롭 패턴, 개발 서버 기준 LCP 등 성능 개선점 (위 필수에 해당하지 않는 것)
   - `DESIGN.md`의 **승인 표시**(`[승인: 시안 X]`, `[승인: 사용자 지시]`, `[승인: 프리셋]`, `[기존]`)가 면제하는 것은 **값의 선택**(색, 간격, 크기 단계, 반경, 레이아웃 문법)뿐이다 (`design-setup.md` 5-3절). 승인된 값으로 만든 화면에서도 `slop-tells.md` 2절 징후가 보이면 점검한다. 다만 승인 값 자체를 바꿔야 고칠 수 있으면 고치지 말고 **권장**에 "승인 값 · <무엇>"으로 적어 사용자가 정하게 한다. `[AI]`이거나 표시가 없는 값은 다른 값과 똑같이 점검한다. 승인된 값도 대비와 접근성 기준, 고정 규칙은 그대로 적용한다.
7. **필수** 항목은 모두 수정한다. 확정 구조와 달라진 곳은 확정 구조대로 고치거나, 사용자에게 알리고 판정을 받는다. **권장** 항목은 고치기 쉬운 것만 고치고, 나머지는 완료 보고에 목록으로 남겨 사용자가 고를 수 있게 한다.
8. 수정 후 재점검은 **1회만** 한다. 고친 화면과 폭만 다시 띄워 확인한다. 재점검에서 새로 나온 필수 항목은 고치고, 그 이상 반복하지 않는다.
9. 데스크톱(1280)과 모바일(375) 캡처를 `.claude/screendoro-approved/`에 "승인 대기"로 저장한다 (Playwright 폴백이면 `--approved`). 사용자가 받아들인다고 하면 "승인"으로 바꾼다 (`consistency.md` 5-1절).
10. 그 다음에 완료로 보고한다.

## 완료 보고 형식

완료 보고는 3~5줄로 끝낸다:

- 단계: 수행한 단계와 건너뛴 단계를 한 줄로 (예: "0-1 수행 · 1 수행(분할형 히어로) · 2 건너뜀 · 3 화면 2개(뻔함 점검 수정 3 · 자기 비평 캡처 기준) · 4 수행")
- 초안: 차이 건수를 찾은 쪽과 판정으로 나눠서 (예: "차이 5건(사용자 지적 3 · AI 공개 2) → 초안대로 3 · AI안 1 · 절충 1"). 건너뛰었으면 "초안 없음(사용자가 건너뜀)"
- 검증: 확인한 폭, 콘솔·네트워크 결과, 측정했다면 LCP·CLS 값 (예: "375/768/1280 확인 · 콘솔 오류 0 · CLS 0.02, LCP 1.4s(개발 서버)"). 띄워 보지 못했으면 "렌더링 미검증"과 이유
- 수정: 고친 필수 항목 수와 대표 항목 1~2개 (고정 규칙 위반을 고쳤으면 따로 표시)
- 남은 권장 항목: 있으면 짧은 목록, 없으면 생략
- 실제 자료로 바꿀 것: 교체 자리(`TODO(screendoro)`)와 예시 데이터 중 실제 자료가 필요한 곳이 있으면 짧은 목록 (`landing-strategy.md` 9-2, `design-setup.md` 3-5)
- 2단계를 수행했으면 시안 방식, 고른 시안 한 줄, 레퍼런스 기반이면 근거 번호
- 키트: 쓴 섹션 유형 수와 새로 만든 키트 항목(승인 대기). 예: "키트 조립 · 섹션 유형 4종 사용 · 새 틀 1개(승인 대기: 가격 비교)". 거절 피드백을 받았으면 바꾼 축
- `DESIGN.md`에 `[AI]` 값이 있으면 짧은 목록으로 적는다. 사용자가 받아들이면 `[승인: 사용자 지시]`로 바꾼다
- Astryx 프로젝트면 "단계" 줄에 Astryx 사용을 적고, `swizzle`한 컴포넌트가 있으면 이름을 적는다

## 금지 사항

- 사용자의 초안을 받기 전에 구조, 섹션 구성, 레이아웃, 디자인 방향을 제안하지 않는다. 예시 구조나 선택지도 먼저 내지 않는다.
- 사용자가 명시하지 않았는데 0-1단계를 건너뛰거나, 건너뛰자고 먼저 권하지 않는다.
- 초안을 기록할 때 다듬거나, 빈칸을 채워서 사용자의 초안인 것처럼 적지 않는다.
- 구조안을 처음 보여줄 때 차이를 먼저 표시하지 않는다. 사용자가 지적한 뒤에는 남은 차이를 하나도 빼지 않고 공개한다.
- 차이의 판정이 끝나기 전에 시안, 랜딩 전략 결과물, 화면 코드를 만들지 않는다.
- 판정을 받지 않고 확정 구조와 다르게 만들지 않는다. 사용자가 정한 판정을 다시 주장하지 않는다.
- 3단계 없이 화면 코드를 작성하지 않는다.
- 구조 와이어프레임을 확정하기 전에 스타일 시안을 그리지 않는다.
- 코드 키트가 있는 프로젝트에서 키트를 쓰지 않고 같은 부품을 새로 그리거나, 키트 부품을 화면마다 다시 스타일링하지 않는다.
- 거절 이유를 묻거나 기록하지 않고 다시 그리지 않는다. 사용자 허락 없이 `~/.claude/screendoro-taste.md`에 쓰지 않는다.
- 3-1 계획과 3-2 뻔함 점검 없이 화면 코드를 쓰지 않는다. `slop-tells.md`를 읽기 전에 시안이나 화면 코드를 만들지 않는다.
- 랜딩 작업에서 1단계 결과물 없이 화면 코드를 작성하지 않는다.
- 랜딩이 아닌 작업에 `landing-strategy.md`를 적용하지 않는다.
- 사용자가 고르지 않았는데 `landing-visual-preset.md`의 값을 적용하지 않는다.
- 4단계를 생략하거나, **필수** 항목을 남긴 채 완료로 보고하지 않는다.
- 이중 테두리, 불필요한 밑줄·장식 요소, 각진 버튼, 경기천년체가 아닌 폰트를 쓰지 않는다. `DESIGN.md`나 프리셋에 다르게 적혀 있어도 마찬가지다. 예외는 사용자 지시와 `house-rules.md` 1-1절에서 사용자가 고른 폰트 예외뿐이다.
- 기존 폰트가 있는 프로젝트에서 사용자에게 묻지 않고 폰트를 경기천년체로 바꾸지 않는다.
- 경기천년체 웹폰트 주소를 지어내지 않는다. 파일을 못 구했으면 보고에 "경기천년체 파일 미적용"이라고 적는다.
- 4단계 재점검을 2회 이상 반복하지 않는다.
- 화면을 띄워 보지 않고 "레이아웃 문제 없음", "콘솔 오류 없음"이라고 보고하지 않는다. 띄울 수 없으면 미검증으로 적는다.
- 측정하지 않은 성능 수치를 추정해서 적지 않는다.
- Lighthouse, Playwright, 브라우저 같은 도구를 사용자에게 묻지 않고 새로 설치하지 않는다.
- 이미 불러온 스킬을 같은 세션에서 다시 불러오지 않는다. 단, 대화 요약으로 지침 본문이 사라졌으면 다시 불러온다.
- 사용자 확인 없이 파일을 지우지 않는다 (오래된 승인 캡처 정리 포함).
- 이미 마커가 있는 프로젝트에서 사용자 요청 없이 2단계를 다시 하지 않는다.
- 2단계에서 사용자가 시안을 고르기 전에 `DESIGN.md`나 토큰을 확정하지 않는다.
- 사용자가 보거나 정하지 않은 값에 승인 표시를 달지 않는다. `[AI]` 값을 이유가 있다는 까닭으로 슬롭 점검에서 빼지 않는다.
- 레퍼런스 사이트의 로고·이미지·문구·에셋을 가져오거나, 한 사이트의 레이아웃을 구조째 복제하지 않는다. 패턴과 원리만 가져온다.
- 레퍼런스 사이트에서 측정하지 않은 값을 측정값처럼 적지 않는다.
- 사용자가 레퍼런스 방식을 고르지 않았는데 레퍼런스를 수집하지 않는다. 마커가 있는 프로젝트에서도 요청 없이는 하지 않는다.
- **레퍼런스 없이** 방식에서 레퍼런스 노트나 갤러리를 시안 근거로 쓰지 않는다.
- 2-1 시안 선택은 최초 구성 때만 한다. 마커가 있는 프로젝트의 이후 화면 작업에서는 사용자가 요청하지 않는 한 시안을 그리지 않는다.
- 사용자가 고르지 않았는데 Astryx를 설치하지 않는다. 마커의 `componentLib`이 `"astryx"`가 아닌 프로젝트에 `references/astryx.md`를 적용하지 않는다.
- CLI를 설치하기 전에 `npx astryx`를 실행하지 않는다. 항상 `npx @astryxdesign/cli`를 쓴다.
- Astryx 컴포넌트의 props와 토큰 이름을 기억으로 쓰지 않는다. CLI로 조회해서 쓴다.
- Astryx 플러그인 설치, 전역 설치, `swizzle`을 사용자에게 묻지 않고 하지 않는다.
